## Executive summary

v0.3.6 is internally versioned consistently and its release workflow completed successfully, including Godot parsing, a short headless smoke run, Android export, and signing verification. The connection graph and pre-validation approach are good foundations.

The highest-priority follow-up items are:

1. Correct the release-certificate fingerprint in `SIGNING.md` and verify which fingerprint is authoritative for every permanent-signed release.
2. Preserve the v0.3.6 mount-relative reset basis through Undo/Redo snapshots.
3. Decide and document the intended collision policy, then enable collisions between disconnected pieces/assemblies if normal physical interaction is intended.
4. Add headless behavioral tests; the current CI smoke test cannot detect any of the above.

## Confirmed findings

### P1 — `SIGNING.md` publishes a different certificate fingerprint from the release workflow

Evidence:

- `SIGNING.md:5-8` calls `24:A4:0D:73:4E:EC:AF:5B:E2:75:CF:C1:4C:71:7C:B0:F7:51:D7:E7:C1:DF:99:E8:89:5E:F6:27:12:A2:A4:55` the permanent release certificate.
- `.github/workflows/android.yml:21` enforces `BF:CD:2B:59:70:91:E4:AA:FE:4F:27:93:FD:14:A7:9A:2A:D4:94:0D:D1:06:9D:18:74:9C:E7:A9:99:50:D4:22`.
- Git history shows commit `55576d4` changed the workflow from the first fingerprint to the second without updating `SIGNING.md`.
- [Release workflow run #59](https://github.com/pixel375/connex/actions/runs/34168736239) succeeded, so CI found the second fingerprint in the release keystore and exported APK.

Impact: maintainers following the signing guide can verify or back up the wrong key. This is especially risky because losing or changing the real Android signing identity prevents in-place updates.

Recommendation: verify the signer on the published v0.3.6 APK independently, update `SIGNING.md` to the authoritative fingerprint, and add a CI consistency check so the documented value cannot drift from the workflow value.

### P1 — Undo/Redo loses the v0.3.6 mount-relative placement-reset baseline

Evidence:

- `scripts/main_v036_mount_home.gd:10-15` stores `mount_home_relative_basis_v036` only as metadata on a live joint.
- `scripts/main_v020.gd:1568-1587` serializes connection metadata for history, but not that new basis.
- `scripts/main_v020.gd:1644-1652` restores the older connection fields, but not the new basis.
- `scripts/main_v020.gd:1659` then rebuilds the graph. The derived `_tag_connection_v020()` sees the metadata is absent and initializes it from the restored current transforms.

Likely reproduction:

1. Create a socket, cross, or axle-mounted connector.
2. Roll it by 45 degrees.
3. Undo, then Redo the roll.
4. Press **Reset Placement Rotation**.

After Redo, the rolled orientation has been recorded as the new home, so Reset can become a no-op instead of returning to the original placement orientation. Delete/Undo and other history restores can cause the same loss.

Recommendation: include the relative home basis in each saved connection record and restore it onto the joint before `_rebuild_connection_graph_v020()` runs. Add regression coverage for socket, cross, and axle mounts across Undo/Redo and Delete/Undo.

### P1 — Regular rods and connectors do not collide with one another during simulation

Evidence:

- `scripts/main_v012.gd:299-305` puts each regular piece on collision layer `2` but gives it collision mask `1` only.
- The ground is on layer `1`, so pieces collide with the ground.
- Other rods/connectors are on layer `2`, which neither regular piece scans. Disconnected pieces and assemblies therefore pass through one another.
- `scripts/main_v014.gd:608-617` builds collision exceptions for bodies in the same fixed component. Those exceptions are redundant while regular body-to-body collisions are globally filtered out.
- The README describes suppression of self-collision *inside rigid fixed components*, which implies different components are expected to collide.

Impact: simulation cannot model contact between separate mechanisms or falling loose pieces, and the result differs from the documented collision policy.

Recommendation: if inter-assembly contact is intended, include the construction-piece layer in regular-piece masks and retain exclusions only for bodies that belong to the same rigid component or direct joint. Add a two-loose-pieces physics test. If global non-collision is intentional, simplify the exception code and document the limitation explicitly.

### P2 — CI has no behavioral regression tests

`.github/workflows/android.yml:112-119` parses the project and runs the main scene for only two seconds. This proves that scripts load and startup does not immediately fail, but it does not exercise attachment replacement, graph invariants, Undo/Redo, reset behavior, collision response, updater parsing, or simulation constraints.

Recommendation: add a headless Godot test scene or test runner covering at least:

- socket/cross/axle/O-Ring creation and validation;
- atomic attach replacement and occupied-port rejection;
- primary-pivot preservation after reattachment;
- reset after Roll, Undo/Redo, and Delete/Undo;
- disconnected-body collision and same-component collision exclusion;
- snapshot round trips preserving every piece and connection field;
- version comparison and release-asset selection.

### P2 — The active implementation is a 16-level, 11,805-line inheritance chain

`Main.tscn` loads `main_v036_mount_home.gd`, which inherits through every active version script back to `main_v012.gd`. Many methods are overridden repeatedly and depend on dynamic dispatch through older `super` implementations. Examples include `_ready`, `_build_ui`, `_update_ui`, `_process`, `_status`, `_on_update_request_completed_v021`, attachment picking, rotation validation, and state restore.

Impact:

- A fix in a new version can omit a state field owned by an older snapshot layer, as happened with the mount-home basis.
- Old UI and updater logic is still constructed or executed before newer layers hide or supersede it.
- It is difficult to determine which implementation is authoritative and easy to introduce order-dependent side effects.

Recommendation: flatten the version chain before adding large new features. Keep historical code in tags/branches, and split the current runtime into focused components such as `PieceFactory`, `ConnectionGraph`, `BuildHistory`, `EditorController`, `SimulationAssembler`, `Updater`, and UI views.

### P2 — UI refresh recomputes the connection graph and rotation candidates repeatedly

The inherited `_update_ui()` chain performs duplicate work:

- `main_v030.gd:233-257` computes two Roll candidates and refreshes all six gizmo directions.
- `main_v032.gd:219-229` refreshes attachment points, which rebuilds the graph.
- `main_v035.gd:188-201` computes two more Roll candidates and refreshes all six gizmo directions again.
- Each `_rotation_candidate_v030()` calls `_rotation_context_v030()`, which rebuilds the full graph before traversing and validating the component.

One final v0.3.6 UI update can therefore perform roughly sixteen rotation-context/graph calculations plus attachment graph work. This has not been benchmarked, but it scales with assembly size and is unnecessary duplicate computation.

Recommendation: compute one graph/context snapshot per mutation, derive all direction states from it, cache the result until topology or transforms change, and remove superseded parent refresh work during the flattening refactor.

### P2 — Auto-fusion uses full-scene brute-force searches on every commit

`scripts/main_v020.gd:1012-1134` scans all connectors and sockets for each rod end, then scans all rods for each connector socket, for up to five passes. `_commit_state()` runs auto-connect before each history commit.

Impact: larger builds will trend toward quadratic work, multiplied by the retry passes and subsequent graph rebuilds.

Recommendation: maintain a spatial index of socket points and rod segments, query only nearby candidates, and limit auto-fusion to pieces/components whose transforms changed in the current command.

### P2 — Procedural visuals create a high node and draw-call count per piece

`scripts/main_v015.gd:604-638` builds a rod from many separate `MeshInstance3D` nodes. `scripts/main_v015.gd:641-703` builds connectors similarly; an eight-way connector creates dozens of separate mesh nodes. Mesh materials are cached, but mesh resources and combined geometry are not.

Impact: scene-tree overhead and draw calls will become a mobile bottleneck well before raw polygon count does. Undo/Redo recreates all of these nodes for the entire build.

Recommendation: prebuild and cache one combined mesh per part type (and per fixed rod length), reuse shared mesh resources, and keep one or very few `MeshInstance3D` nodes per physical body. Profile draw calls and frame time on a representative low/mid-range Android device.

### P2 — Undo/Redo rebuilds the complete runtime scene for every step

`scripts/main_v013.gd:841-891` queues every current body and joint for deletion, then recreates all bodies, visuals, and joints from a full snapshot. History keeps up to 80 full model snapshots (`main_v013.gd:893-902`).

Impact: history operations scale with total build size, create transient allocation spikes, and make it easy to lose newly introduced metadata during serialization.

Recommendation: define a canonical serializable model and either apply model diffs incrementally or use command-based history. At minimum, centralize snapshot serialization/deserialization with a schema version and a round-trip invariant test.

### P2 — Collision shapes are much coarser than the rendered/mechanical geometry

`scripts/main_v015.gd:698-703` represents every connector, including the open center and separated jaws, as one solid cylinder of radius `1.46`. Rods use one capsule. This is fast, but it makes the hub and jaw openings physically solid for unrelated pieces and makes physical picking treat empty connector space as part of the connector.

Recommendation: after establishing the intended collision policy, use a small compound of primitive shapes around the hub/jaws or another simplified concave-safe representation. Keep interaction-picking shapes separate from simulation collision shapes if their needs differ.

### P2 — Updater integrity checks are optional when GitHub omits an asset digest

`scripts/main_v033.gd:309-312` compares SHA-256 only when `apk_expected_sha256_v033` is non-empty. If the API omits `asset.digest`, any HTTPS response larger than 1 MiB is accepted and opened. The release workflow already publishes a `.sha256` asset but the updater does not use it as a fallback.

Recommendation: require a digest for in-app installation, or download and validate the published checksum asset when the API digest is absent. Select the APK by an exact expected naming rule rather than taking the first `.apk` asset, so future multi-ABI/debug assets cannot be chosen accidentally.

### P2 — Release workflow permissions and trigger can be tightened

- `.github/workflows/android.yml:9-10` grants `contents: write` to the whole workflow, including pull-request builds. Use read-only default permissions and grant write only to an isolated release job.
- The release is triggered by `[release]` appearing in a main-branch commit message while the tag/name are hard-coded. A stale version bump or repeated trigger can target the wrong existing release. Prefer a validated `v*` tag trigger or a manual release input with consistency checks.
- Pin third-party actions to immutable commit SHAs for stronger supply-chain control.
- [Run #59](https://github.com/pixel375/connex/actions/runs/34168736239) reports a Node.js 20 deprecation warning for the current action versions; update them to supported releases.
- Consider verifying checksums for the downloaded Godot binary and export templates before executing them.

### P3 — Version data is duplicated across code, export settings, workflow, filenames, and docs

The v0.3.6 string appears in the current script, export preset, workflow artifact/release names, README, release notes, and help/status text. The active inheritance chain also contains every prior version constant and repeated updater comparisons.

Current v0.3.6 values are consistent, but future release drift is likely.

Recommendation: define one runtime version source and add a release validation script that checks `version/name`, monotonically increasing `version/code`, tag, APK name, release notes title, README, and updater current-version comparison.

### P3 — Legacy files and runtime UI remain in the shipped project

- `scripts/main.gd` is an unreferenced v0.1.1 implementation.
- `scripts/main_v014_orings.gd` is not in the active inheritance chain.
- `scripts/rotation_gizmo_screen.gd` is still loaded and instantiated by the v0.3.4 layer, then hidden/retired by v0.3.5.
- `export_presets.cfg` uses `export_filter="all_resources"`, so unreferenced resources may still be packaged.

Recommendation: remove or archive dead runtime files after the active code is flattened, stop instantiating retired controls, and export only required resources.

### P3 — The right-side layout still depends on hard-coded pixel heights

`scripts/main_v036.gd:84-112` mixes viewport height with fixed top, bottom, collapsed, and open-panel sizes. On unusually short or resized viewports, `bottom_limit` can be forced below the usable viewport and content is merely clipped, which can make controls inaccessible.

Recommendation: use container-driven layout with a `ScrollContainer`, safe-area handling, and automated checks at representative aspect ratios and Android display cutouts.

### P3 — GitHub issue #12 appears stale

[Issue #12](https://github.com/pixel375/connex/issues/12) remains the only open issue and describes the v0.3.0 transform gizmo and explicit topology editor. Most of that work is present in v0.3.0-v0.3.6.

Recommendation: close it with links to the implementing releases/PRs, or split genuinely unfinished details into focused current issues.

## Positive findings

- `Main.tscn`, runtime status/help, Android `version/name`, APK filename, workflow release/tag, README, and release notes all identify v0.3.6; `version/code=17` is incremented from v0.3.5.
- The v0.3.6 release workflow succeeded and produced a 24.9 MB signed artifact.
- No obvious credentials, private keys, or password values are tracked; sensitive signing filenames are ignored.
- Attachment replacement validates the prospective transforms before removing the old graph edge, which is the right transactional shape.
- Piece and connection UIDs make model-level persistence and focused automated tests practical.
- Update downloads use HTTPS, enforce a minimum size, and verify GitHub's SHA-256 digest when present; Android signing adds another important update boundary.
